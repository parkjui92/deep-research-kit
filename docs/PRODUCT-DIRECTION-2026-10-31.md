# Deep Research Kit 제품 방향·UI 재설계 제안

조사일: 2026-10-31 · 상태: 설계 제안, 미구현 기능은 아래에 별도 표시

## 결론: ‘문헌을 찾는 일’과 ‘보고서에 쓰는 일’을 연결한다

**제품 약속: 주제에 맞는 문헌을 찾고, 보고서에 쓸 근거로 정리합니다.**

사용자는 우선 과제로 ① 모아 둔 논문·보고서 비교 및 인용 근거 확인, ② 낯선 주제의 핵심 문헌·연구 흐름 찾기를 함께 선택했다. 따라서 PDF 검토 전용 도구로 좁히거나, 범용 AI 검색을 전면에 내세우는 것 모두 요구의 절반을 놓친다. 두 시작 경로를 한 결과물로 연결하는 것이 권고안이다.

> 주제로 문헌 찾기 / 내 문헌 가져오기 → 내 질문에 맞춘 비교표 → 실제로 사용할 근거 확인 → 출처와 함께 보고서에 가져가기

주 사용자는 여러 문헌을 근거로 보고서·논문 초안을 작성하는 연구자·분석가로 가정한다. 이는 제품 가설이며 사용자 인터뷰로 검증한 세분시장은 아니다. 강의·학습 모드는 부가 경로로 유지하되 기본 화면의 구조를 결정하게 하지 않는다.

완성 결과는 단순 요약문이 아니라 **문헌별 대상·방법·결과·조건을 나란히 놓은 비교표와, 채택한 근거에 원문 위치가 연결된 근거 브리프**다. 낯선 주제에는 먼저 읽을 문헌과 선정 이유가, 이미 모은 문헌에는 비교 가능한 내용과 확인할 차이가 필요하다.

## 유사 도구를 화면과 행동 단위로 분석

### Elicit — 결과에서 근거까지 맥락을 유지한다

**관찰.** [공개 보고서](https://elicit.com/review/20172d4d-4587-4a13-b797-8673475b57a9)는 질문·요약을 본문에, 수집·선별·추출·보고서 진행 상태를 오른쪽에 배치한다. 상단의 추출 단계로 이동하면 문헌×항목 표가 나온다. 셀의 작은 인용 버튼을 누르자 같은 화면 오른쪽이 Supporting quotes와 Explanation으로 바뀌고 선택한 셀이 강조됐다. 발췌를 이전·다음으로 이동할 수 있어 표와 원문을 왕복해도 위치를 잃지 않는다.

**장점의 원리.** 결과물·선택·출처가 같은 문맥에 남는다. 작업 단계는 상단의 작은 구조로 유지하고, 선택된 대상의 상세만 바꾼다. ‘출처가 있다’는 문구보다 클릭 한 번으로 확인되는 근거가 신뢰 형성에 유용하다는 설계 가설이다.

**그대로 가져오면 안 되는 점.** 관찰한 1280px 화면에서는 좌측 탐색·우측 상세가 각각 공간을 차지해 추출표에서 보이는 열이 적고 행이 매우 높았다. 우리 앱도 표·원문을 무조건 3단으로 나누면 같은 문제가 생긴다. 기본은 비교표+접을 수 있는 근거 패널 2단, 긴 PDF는 별도의 확대 보기로 한다.

**최신성 주의.** 이 공개 보고서는 2025년 생성 자료다. 현재 공식 안내는 Research Agent·Research Report·Systematic Review 세 시작 경로를 설명하며, 과거 Find Papers·Extract Data·Chat with Papers는 2026-09-30 Research Agent에 통합됐다고 명시한다. 오래된 ‘Find Papers 첫 화면’을 현재 대표 UI로 삼지 않는다. [공식 시작 안내](https://support.elicit.com/en/articles/14757543-getting-started-with-elicit-which-workflow-should-i-use)

**적용.** 선택한 셀 옆에 근거를 열고 결과 브리프의 인용에서도 같은 셀로 돌아온다. 내보내기를 마지막 팝업으로 숨기지 않고, 처음부터 완성 예시를 보여준다. 프로젝트·실행 이력은 필요할 때만 연다.

### Liner — 사용자가 얻을 효용을 먼저 말한다

**관찰.** [실제 비로그인 시작 화면](https://scholar.liner.com/ko)은 출처에 관한 불안을 해결한다는 제목과 큰 입력창이 중심이다. 맥락 추가, 스킬, 풀 텍스트 선택이 입력창에 붙어 있다. 스킬 메뉴에는 관련 논문 찾기·인용 추가·초안 작성 등에 해당하는 명령이 보였다. [공식 Scholar 소개](https://liner.com/ko/scholar)는 논문 찾기·비교·문헌 검토처럼 작업별 효용을 보여준다. 비교 예시는 PDF 3개를 입력하고 연구 질문·방법 등의 항목으로 비교표를 받는 형태다.

**장점의 원리.** 프로젝트 구조를 먼저 익히지 않고, 자료와 요청에서 출발한다. 입력 가까이에 결과 예시가 있어 무엇을 요청할지 추측하기 쉽다. 반면 실제 시작 화면의 자유 입력과 영어 슬래시 명령은 초보자에게 여전히 프롬프트 작성 부담을 남길 수 있다. 이는 관찰에서 도출한 가설이며 사용자 시험 결과가 아니다.

**적용.** 우리 앱은 ‘무엇이든 물어보세요’ 대신 ‘어떤 주제를 조사하나요?’와 ‘어떤 문헌을 비교하나요?’를 구체적으로 묻는다. 비교할 항목은 연구자 언어로 추천하되 수정 가능하게 한다. “출처 검증 완료” 같은 일괄 표시는 쓰지 않고 원문 위치·사람의 검토·읽은 범위를 분리한다. [공식 비교 예시 이미지](https://assets.liner.com/web/liner-com/main/scholar-useacse-2.webp)

### Rayyan — 반복 판단을 하나의 동작 흐름으로 만든다

**공식 문서 관찰.** 선별 화면은 왼쪽 문헌 목록, 가운데 상세, 선택적으로 여는 오른쪽 필터로 구성된다. 포함·보류·제외·이유·라벨을 판단 영역에 모으고, 미결정 문헌에 집중해 결정 후 다음 문헌으로 이동한다. 단계마다 판단 대상도 제목/초록→전문→추출로 명시한다. [선별 가이드](https://help.rayyan.ai/hc/en-us/articles/45703234075281-How-to-Screen-References-in-Rayyan)

**적용.** ‘문헌을 조사에 포함할지’와 ‘추출된 내용을 보고서에 쓸지’를 서로 다른 말과 위치로 구분한다. 검토 중에는 문헌 추가·AI 설정을 크게 노출하지 않는다. 채택·수정·보류를 같은 위치에서 수행하고 다음 미검토로 이어간다. 다만 이 앱은 검토자·이유·문맥 확인을 요구하므로 Rayyan의 자동 저장을 그대로 복사하지 않는다. 수정 입력은 수정 선택 시에만 열고, 이유는 구체적인 선택지+직접 입력으로 줄일 수 있다. [Workbench 설명](https://www.rayyan.ai/workbench)

### ResearchRabbit — 검색 결과를 다음 탐색의 출발점으로 쓴다

**공식 문서 관찰.** 키워드·DOI·기존 컬렉션·서지 파일에서 출발해 관련 문헌을 씨앗으로 고른다. 결과 중 고른 논문들이 다음 탐색의 입력이 되고, 탐색 단계를 돌아보거나 컬렉션에 저장한다. [검색 가이드](https://learn.researchrabbit.ai/en/articles/12454528-how-to-search-in-researchrabbit)

**적용.** 검색 결과의 ‘담기’만 제공하지 말고 ‘이 문헌에서 더 찾기’를 연결한다. 먼저 인용·참고문헌·유사 주제의 목록과 관계 이유를 제공하고, 실제 연결 데이터와 사용성이 확보된 뒤 그래프를 고려한다. 인용 수나 연결 중심성을 곧 연구 품질로 표시하지 않는다. 사용자가 무엇을 선택했는지와 어느 검색에서 발견했는지 계속 보이게 한다.

## 페인포인트 중심 고도화

### 1. “처음 보는 주제라 어디서부터 읽을지 모르겠다”

**해야 할 일.** 질문 한 문장을 넣으면 먼저 읽을 후보와 그 이유를 받아 핵심 문헌 3~5편을 고른다. ‘핵심’은 절대 순위가 아니라 질문·기간·분야에 따른 후보라는 점을 드러낸다.

- 첫 화면: 조사 주제, 선택적 기간/분야. 검색 자료원과 세부 수식은 ‘검색 범위’에 접는다.
- 결과: 제목·연도·자료 유형·관련 이유·초록의 해당 문장·전문 확보 여부. 관련 이유는 실제 메타데이터/초록에 근거하며 AI 추천이면 표시한다.
- 문헌의 역할: 개관용/직접 실증/최근 동향 등. 분류 근거가 없으면 ‘분류 안 됨’으로 둔다. 피인용순을 품질순으로 부르지 않는다.
- 후보함: 선택한 문헌과 조사 질문을 유지하고 ‘선택한 문헌 비교하기’로 연결한다. 검색을 바꿔도 후보를 잃지 않는다.
- 확장: 특정 논문에서 인용한/인용된 문헌, 유사 주제를 각각 구분해 찾는다. 관계 데이터가 없으면 기능을 가장하지 않는다.
- 빈 결과/자료원 실패: 실패한 자료원·현재 검색 범위를 드러내고, 검색어 변경·다른 자료원·PDF 가져오기 중 가능한 다음 행동을 준다.

**구현 차이.** 현재 키워드 검색·필터·이력은 재사용 가능하다. 지속 후보 목록, 설명 가능한 관련도, 관계 탐색은 신규 기능이다. 한국어 질문을 영어 검색어로 확장할 때 원래 질문과 실행 검색어를 함께 보존한다. 국내 보고서 탐색은 현재 자료원이 보장하지 않으므로 수동 PDF 경로와 향후 자료원 확장을 구분해 안내한다.

### 2. “자료는 모았는데 문헌마다 말하는 조건과 수치가 달라 정리가 안 된다”

**해야 할 일.** PDF들을 같은 질문에 대해 비교하되 서로 다른 지표를 억지로 하나의 결론으로 합치지 않는다.

- 비교 템플릿: 대상/맥락, 방법/비교 기준, 결과/단위, 적용 한계. 사용 목적별로 조정 가능하게 한다.
- 각 값에는 지표·단위·기간·조건과 읽은 범위를 보존한다. 모호하거나 없는 정보는 ‘미기재/읽은 범위에서 못 찾음/추출 실패’를 구분한다.
- 같은 열에 다른 지표가 섞이면 ‘직접 비교 어려움’과 이유를 표시한다. 근거가 모일 때만 동의·차이를 제안하고 사람이 확인한다.
- PDF 파싱 가능 여부와 일부 페이지만 읽는지 먼저 보여준다. 스캔 문서는 본문을 읽은 것처럼 처리하지 않는다.

**차별화 가설.** 대량 자료원 규모보다, 한국어 질문과 논문·보고서의 다양한 문체를 비교 가능한 근거로 바꾸는 반복 작업에 초점을 둔다. 아직 한국어 PDF 추출 품질이 검증됐다는 뜻은 아니다. 국내 보고서·다단 논문·표 중심 PDF로 별도 평가셋이 필요하다.

### 3. “AI 요약을 보고서에 인용해도 되는지 다시 확인하느라 시간이 든다”

**해야 할 일.** 실제로 쓸 내용부터 원문 문맥과 확인하고 수정 기록을 남긴다.

- 비교표 셀 선택 → 옆에 추출 내용·원문 발췌·쪽수·읽은 범위 → 문맥 확인 → 채택/수정/보류/제외.
- ‘보고서에 사용할 후보’는 사용자의 편집 의도이고 ‘채택’은 검토 결과다. 별도 상태로 보존한다. 후보 선택만으로 채택 처리하지 않는다.
- 기본 검토 대기열은 사용 후보, 위치 미확인, 수치/단위 누락 등 설명 가능한 사유에 따라 좁힐 수 있다. 모든 근거에도 접근 가능하다.
- 연구 결론에 들어가는 근거는 계속 명시적 검토를 거친다. 원문 강조나 문자열 일치만으로 자동 채택하지 않는다.
- 보고서 문장과 근거의 연결은 단순 링크만으로 충분하지 않다. 종합 과정에서 범위·단위가 바뀌지 않았는지 주장 수준의 확인을 추가한다.

**검토 부담을 줄이는 방식.** 20편×6항목=120개 추출값을 모두 같은 순서로 처리하게 하기보다, 보고서에 쓸 후보부터 검토한다. 120은 예시 계산이며 처리 시간 절감은 실측하지 않았다. 나머지는 미검토로 남고 채택 결과에 섞이지 않는다. 초안 표는 ‘미검토’ 표시를 유지한 채 별도 출력할 수 있도록 제안한다. 현재 전체 근거 CSV/JSON은 이미 미검토 기록도 보존하므로, 새로 필요한 것은 숨겨진 데이터를 만드는 일이 아니라 결과물의 상태를 명확히 나누는 UI다.

### 4. “논문을 추가하거나 질문을 고치면 작업을 다시 해야 한다”

새 문헌/변경 항목만 추출하고 기존 결과와 차이를 보여주는 기능을 후속 핵심 기능으로 둔다. 원본 해시·항목 정의·읽은 범위·프롬프트/모델 버전에 따라 재사용 가능성을 판단한다. 이전 실행은 보존하고 신규 실행에 부모 관계와 변경 범위를 기록한다. 원문·항목·값이 달라진 근거의 사람 판단은 자동 승계하지 않는다. 근거가 바뀌면 그 근거를 사용하는 브리프도 갱신 필요 상태로 전환한다.

## 권고 정보 구조와 화면 설계

### 시작: 프로젝트 생성보다 실제 작업

메인 문구: **주제에 맞는 문헌을 찾고, 보고서에 쓸 근거로 정리하세요.**

두 입구:

1. **주제로 문헌 찾기** — 조사 질문 입력 → 후보와 선정 이유 → 담기.
2. **내 문헌 비교하기** — PDF/서지 가져오기 → 조사 질문과 비교 항목 확인 → 추출.

두 입구 아래에는 결과 비교표의 작은 예시와 최근 조사만 둔다. 프로젝트 이름·폴더·실행 ID·검토 규칙·AI 공급자 설정을 시작 폼 전체에 펼치지 않는다. 예제 체험은 실제 문헌 업로드나 새 AI 실행을 대신한 것으로 표시하지 않는다.

### 작업 중: 세 개의 공간

| 공간 | 주 대상 | 주 행동 | 보조 정보 |
|---|---|---|---|
| 문헌 모으기 | 검색 결과와 내 후보함 | 선택한 문헌 비교하기 | 검색 범위·자료원·전문 상태·선별 이유 |
| 근거 비교 | 문헌×항목 표 + 선택 근거 패널 | 이번 근거 확인하고 다음으로 | 열/상태 필터·전체 원문·추출 범위 |
| 보고서에 쓰기 | 채택 근거·차이/한계·출처 | 근거 브리프 만들기 / 다운로드 | 미검토 수·포함 범위·갱신 필요 상태 |

전역에는 조사 제목, 새 조사, 최근 조사, 설정만 둔다. 실행 이력은 ‘이전 결과’에 넣고 현재 결과와 다른 질문/범위일 때 차이를 눈에 띄게 알린다. 기본 작업에서 학습 모드를 요구하지 않는다.

### 비교와 검토의 공간 배분

- 넓은 화면: 표 약 60%, 근거 약 40%. 일반 상태에서는 표의 텍스트를 2~3줄로 제한하되 선택하면 전체 값을 패널에서 읽을 수 있다. 패널 접기/원문 확대를 제공한다.
- 긴 원문 확인: PDF 자체가 좁아 읽기 어려워지면 읽기 중심 화면으로 확장한다. 표 선택 위치는 유지한다.
- 좁은 화면: 제목과 핵심 결과를 문헌 목록으로 전환하고 근거 상세로 이동한다. 실제 데이터 비교가 필요한 표만 가로 스크롤을 허용한다.
- 검토 행동은 원문 가까이에 모으고, 수정/사유 입력은 현재 판단에 필요한 것만 연다. 색상 외에 ‘미검토·보류·채택’ 텍스트를 유지한다.
- ‘위치 찾음’, ‘본문 확보’, ‘사람이 채택’은 서로 다른 상태다. 한 초록색 체크로 통합하지 않는다.

### AI 실행은 시작 가능한 상태부터 분명하게

현재의 Claude Code/웹 AI 연계를 단순히 팝업 뒤에 숨기는 것으로 실행 경험이 해결되지는 않는다. 시작 단계에서 연결 준비 여부를 확인하고, 실행 직전에 대상 문헌·항목·페이지 범위·실행 방법을 한 번에 보여준다. 실제 예상치가 없으면 시간/비용 수치를 만들지 않는다. 진행 중에는 완료/실패/대기 문헌을 보여주고, 일부 실패 시 저장한 결과를 유지한다. ‘요청문+JSON’ 경로는 유지할 수 있으나 일반 사용자용 주 경로로 내세우지 않는다. 공급자 확장은 인증·비용·자료 처리 정책을 포함한 별도 기능이다.

지금은 뒤로 미룰 것: 범용 채팅 중심 화면, 자동 연구 공백 확정, 대규모 인용망 장식, 팀 권한/공동 심사, 자동 논문 작성 전 과정을 한 번에 제공하는 약속. 사용자가 선택한 두 작업의 성공 여부부터 확인한다.

## 사용자 검증 계획 — 수치는 목표이며 달성 실적이 아니다

서로 다른 숙련도의 목표 사용자 5~6명으로 첫 평가를 제안한다. 작은 표본으로 일반적인 효과 크기를 주장하지 않고, 막히는 행동을 찾아 수정하는 데 쓴다. 현재 화면과 시안의 순서는 교차 배치하고 같은 문헌/질문을 사용한다. 신규 AI 생성 시간과 UI 조작 시간은 따로 측정한다.

| 과제 | 볼 것 | 초기 합격 목표 |
|---|---|---|
| 첫 화면을 보고 설명하기 | 누구의 어떤 문제를 해결하고 무엇이 남는지 | 5명 중 4명 이상이 도움 없이 문헌 찾기/비교/근거 결과를 설명 |
| 낯선 주제에서 첫 문헌 3편 고르기 | 검색어 수정, 선정 이유 이해, PDF 유무 구별 | 외부 생성 대기를 제외한 5분 안에 3편 선택, 고른 이유 설명 |
| PDF 3편에서 한 결과 비교하기 | 항목 선택과 원문 왕복, 대상·단위 혼동 | 별도 사용법 설명 없이 비교표에서 원문 위치 찾기 |
| 조건이 빠진 추출값 수정하기 | 원문 문맥, 수정/이유, 검토 상태 | 5명 중 4명이 의도한 오류를 발견하고 수정. 위치 일치를 검토 완료로 오인하지 않음 |
| 근거 2개를 보고서에 가져가기 | 최종/초안 구별, 출처 역추적 | 최종에 미검토 근거 0건. 출처 클릭으로 해당 근거에 복귀 |
| 새 문헌 추가 후 다시 오기 | 기존 선택·판단·필터 보존 | 데이터 손실 0건. 새로 처리할 범위를 설명 가능 |

지속 지표는 검색 건수나 AI 생성량보다 ‘원문과 연결된 채택 근거를 결과물에 가져간 조사 비율’, 첫 근거까지 걸린 시간, 비교표→원문→복귀 횟수/시간, 중도 포기 지점, 조건·수치 수정률을 본다. 수정률이 낮은 것만을 품질 향상으로 해석하지 않는다. 사용자가 오류를 놓쳤을 수도 있기 때문이다.

## 이번 산출물과 다음 구현의 경계

이번 심층 조사에서는 공개 UI/공식 문서와 현재 앱을 비교하고, 두 시작 경로가 공통 비교표·근거·브리프로 이어지는 클릭 가능한 설계 시안을 만들었다. 시안의 문헌·수치·원문은 모두 가상 데이터이며 실제 검색·PDF 업로드·AI 추출·Word 생성은 수행하지 않는다. 시안에서 내보내기 버튼은 출력 구성을 미리 보여준다.

이 문서의 P0/P1/P2는 아직 제품에 구현했다고 주장하지 않는다. 앞선 화면 정리 변경은 현재 작업 트리에 유지되어 있다. 다음 제품 변경은 P0의 두 시작 경로와 비교표/근거 동시 보기부터 검증하고, 사용자 실험으로 문제 정의가 맞는지 확인한 뒤 P1을 진행하는 순서를 권고한다.

### 시안의 브라우저 검증

- 두 입구에서 같은 비교표에 도달, 후보 역할 필터와 선택 유지, 선택한 문헌만 비교표에 표시되는 것을 확인했다.
- 이유 없는 채택을 막고, 문맥 확인 및 이유 입력 후 다음 근거로 넘어가는 동작을 확인했다.
- 수정한 내용이 채택 결과에 반영되고, 미검토 근거는 별도 표시되며, 결과의 인용에서 정확한 원문 패널로 돌아가는 것을 확인했다.
- 1024px에서 표·근거 패널 동시 표시, 360px에서 세로 배치, 320px 시작 화면의 가로 넘침 없음을 확인했다. 모바일의 전용 상세 화면 전환은 향후 제품 구현 사항이다.
- 관찰한 시안의 브라우저 콘솔 오류는 없었다. 이는 프레젠테이션용 로컬 상호작용 검증이며, 실제 검색·AI 추출·Word 생성의 종단 간 검증은 아니다.
