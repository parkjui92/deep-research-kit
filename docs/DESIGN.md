# 화면 설계 원칙

근거 검토실(Streamlit UI)의 시각·구조·문구 규칙과 그 출처를 적는다. 최신 규칙을 먼저 쓰고, 아래의 버전별 기록은 설계 변경 이력으로 보존한다.

## 2026-11-06 · 명시적 시작과 접근 가능한 작업 경로

- 기본 주소는 시작 화면이다. 내 조사와 예시는 사용자가 선택하며, 예시는 안내를 표시한다. 프로젝트 딥링크는 유지한다.
- 비교표에 문헌별 세로 목록을 제공한다. 표 버튼의 문헌 전체 제목·항목명은 화면에서만 잘라 숨기고 접근성 이름에는 남긴다. 검색 결과도 표 셀 편집 없이 한 편을 고르고 저장할 수 있다.
- 좁은 화면에서는 주요 도구를 두 열 또는 전체 폭으로 배치하고, PDF는 화면 너비에 맞춘다. PDF의 자동 위치 이동이 검토 폼과 키보드 초점을 빼앗지 않도록 기본 해제한다.
- 주요 화면에 h1을 두고 집중 검토·복귀에서는 렌더 완료 후 제목으로 초점을 옮긴다. 스크롤용 빈 iframe은 Tab 순서와 접근성 트리에서 제외한다.
- 보고서에 저장된 초안이 있으면 새 세션에서 먼저 보여준다. 사용자가 선택한 결과 종류, 원문 왕복 중 미저장 문단, 노트 검색 조건을 보존한다.

실측 범위와 실제 음성 낭독 검증의 제약은 [검증 기록](VALIDATION.md)을 따른다.

2026-11-07 후속: 페이지 h1 아래의 본문 절은 h2, 시작 경로 카드는 h3로 둔다. 제목마다 반복되는 자동 앵커 링크는 핵심 작업 화면에서 제거한다. 새 질문 폼을 열거나 필수 질문 오류가 나면 첫 입력칸으로, 보고서와 원문을 오가는 버튼에서는 도착한 화면 제목으로 초점을 옮긴다. 평상시 입력이나 라디오 선택 때에는 초점을 강제로 옮기지 않는다. 접힌 사이드바의 컨트롤은 읽기·Tab 대상에서 숨기고, 펼친 메뉴의 접기 버튼은 마우스 위치와 관계없이 접근할 수 있게 한다.

## 2026-11-06 · 연구 작업에 공간을 돌려주기

Elicit·Consensus·ResearchRabbit·Liner·NotebookLM 계열의 공개 가이드와 공식 화면을 비교했다. 관찰 사실, 적용 판단, 미구현 제안은 [UI 벤치마크](BENCHMARK-2026-11-06-UI.md)에 구분했다.

- **탐색은 왼쪽, 작업은 본문**: 밝은 `#F7F8FC` 사이드바에 프로젝트와 문헌 모으기·근거 비교·보고서에 쓰기를 모은다. 현재 위치는 인디고 배경과 굵기로 구분한다. 상세 진행 현황과 설정은 필요할 때 연다.
- **연구 질문은 맥락, 화면 제목은 현재 작업**: 큰 질문·중복 제품명·반복 진행 숫자를 본문 상단에 나열하지 않는다. 질문은 짧은 맥락 행, 비교표는 화면 제목으로 표시한다.
- **표를 바꾸는 행동은 표 바로 위**: 항목 편집과 AI 추출을 같은 도구막대에 둔다. 열의 표시 설정과 실제 추출 지침 편집을 구분한다. 설계가 변경되어도 기존 실행을 덮어쓰지 않으며 이전 기준임을 알린다.
- **집중 검토에는 선택한 근거와 원문**: 표 도구·필터를 접되 값을 유지한다. 돌아가기와 이전·다음은 위에 둔다. 현재 큐 건수와 채택·보류·문자열 위치 상태를 유지한다.
- **쓰기에는 현재 연결 노트 한 건**: 연결 편집은 검색·문헌 필터로 좁히고, 오른쪽은 선택한 노트의 인용·내 메모·쪽수와 원문 이동을 보여준다. 다른 연결 문헌의 철회·정정 경고는 숨기지 않는다. 목차와 미저장 상태를 확인하며 논점 사이를 이동한다.
- **제외한 값도 읽을 수 있게**: 제외 셀의 본문은 `#4B5563`, 배경은 `#F9FAFB`로 둔다. 상태는 색뿐 아니라 낱말·기호를 함께 쓴다. 전체 스크린리더 접근성 인증을 뜻하지는 않는다.

이하의 짙은 사이드바·상단 탭·항상 열린 PDF 등의 설명은 이전 버전 기록이다.

## 이 화면이 하는 일

AI가 낸 추출값 옆에 실제 PDF를 두고 **사람이 판단을 남기는 자리**다. 화면은 세 가지를 늘 구분해 보여 준다.

| 구분 | 뜻 | 표시 |
|---|---|---|
| 위치 대조 | 발췌 문자열이 PDF에 있는가 | `위치 확인` · `위치 미확인` · `미발견` (회색 글자 뱃지) |
| 사람의 검토 | 근거를 어떻게 판정했는가 | `미검토` 파랑 · `채택` 초록 · `수정 후 채택` 초록+연필 · `보류` 주황 · `제외` 회색 |
| AI 종합 | 채택 근거만으로 쓴 초안 | 본문 맨 앞에 "초안" 표시, 주장마다 근거 ID 링크 |

위치 확인은 AI가 옳다는 뜻이 아니다. 미검토는 미완료이므로 파랑(GOV.UK task list: 미완만 강조, 완료는 평문)으로 둔다. 빨강은 오류 메시지에만 쓴다.

## 참고한 것과 가져온 것

조사 2갈래(문헌 검토 도구 8종 · 디자인 시스템 3종 + Streamlit 1.66 문서), 접속 확인 2026-10-31.

| 관례 | 어디서 | 우리 화면 |
|---|---|---|
| 추출값 왼쪽 · 원문 오른쪽, 값을 고르면 해당 쪽으로 이동 | Elicit 추출 표, NotebookLM 번호 인용 | 근거 검토 2단 분할 유지, 발췌 선택 → PDF 쪽·강조 갱신 |
| 판정 3값 이상 + 제외·보류 사유 필수 | Covidence Yes/Maybe/No, Rayyan I/M/E | 채택·수정 후 채택·보류·제외, 이유 필수(코어 규칙) |
| "저장하고 다음" | Elicit Save & next | 판단 저장 뒤 다음 미검토 근거로 자동 이동 |
| 상태별 건수와 진행 막대 | Rayyan 필터, Covidence 태그 건수 | 검토 화면 머리에 진행 막대 + 상태 필터(세그먼트) |
| AI 제시값과 사람 확정값을 따로 | Elicit override, Rayyan 블라인드 | 왼쪽 상자 "AI 추출값", 폼 "수정 후 채택할 값" 분리, 원값 보존 |
| 색 + 글자 (+ 아이콘) 병기, 상태 5~6종 이하 | Carbon status indicator, KRDS 배지 | `st.badge(label, icon, color)` 사전 한 곳(`ui/chrome.py`) |
| 빨강은 오류 전용, 주의는 주황 | GOV.UK tag | 보류 = 주황, 오류 = `st.error` |
| 완료 단계는 평문, 현재·미완만 표시 | GOV.UK task list, KRDS step indicator | 사이드바 단계 목록에 ✓ · ● · ○ 접두 |
| 오류 = 원인 + 해결, 입력값 유지, 폼 옆에 | GOV.UK error message | 채택 확인 누락 → 폼 옆 인라인 오류, 페이지는 유지 |
| 빈 상태는 표 대신 이유 + 다음 행동 하나 | Carbon empty state | 실행 없음·근거 없음·프로젝트 없음에 테두리 상자 + 안내 |
| 숫자 우측·빈 칸 `-`·행 높이 하나 | KRDS 표, Carbon data table | `column_config`, 빈 값 `-` |
| 주색 버튼은 화면당 하나 | KRDS 강조 5% 이하 | 단계마다 `type="primary"` 하나 |
| 8pt 간격, 반경 6px, 본문 17px, 줄간격 150% | KRDS | 테마 `baseRadius=6px`, `baseFontSize=16`, 카드 간격 16·24px |

가져오지 않은 것: 점수·미터 하나로 결론 요약(Consensus Meter는 연구 질·표본을 가중하지 않음), AI 판정의 기본 채택(사람 확정 전 미검토 유지), 색에만 의존한 상태, 단축키 판정(Streamlit 폼 안에서는 불안정), 서지 레코드처럼 보이는 인용(쪽·구간 ID까지 표시).

## 0.3.0 작업 화면 — 결과물(비교표)을 먼저

평가("메뉴를 설명하기보다 사용자가 얻으려는 비교표와 원문을 먼저 보여 줘야 한다")에 따라 기본 화면을 바꿨다. Elicit의 추출 표, Covidence/Rayyan의 큐+상세, NotebookLM의 인용→원문 점프, Zotero의 서지·인용을 한 화면에 모은 구조다.

| 자리 | 내용 | 가져온 관례 |

1440×900 첫 화면에 표와 PDF가 함께 들어오는 것이 기준이다. 학습 모드(단계별 보기)는 0.2.1 배치를 그대로 쓴다.

## 0.2.1 배치 — 벤치마크에서 가져온 것

사용자 평가("UI/UX가 이게 최선이냐, 베스트 사례를 벤치마킹하라")와 페르소나 5명 사용성 시험 뒤 배치를 다시 짰다. 출처는 위 표의 도구들(접속 확인 2026-10-31)과 그 도구들이 공통으로 쓰는 앱 셸 관례.

| 관례 | 어디서 | 우리 화면 |
|---|---|---|
| 제품 이름 + 한 줄 설명이 맨 위, 작업 대상(프로젝트)은 칩으로 | Linear·Notion 앱 머리, NotebookLM 노트북 머리 | `ui.app_header`: 워드마크 「Deep Research Kit」 + 태그라인 + 「프로젝트 · 제목 · 폴더」 칩. 프로젝트 제목을 큰 제목으로 쓰지 않는다 |
| 가로 단계 진행 표시기(완료 ✓ · 현재 강조 · 남은 단계 회색) | Covidence 리뷰 진행, Elicit 온보딩, GOV.UK task list | 머리 아래 6칸 스테퍼. 사이드바 세로 목록과 같은 상태를 두 곳에서 보여 준다 |
| 화면마다 "지금 할 일" 한 문장 + 다음 행동 버튼 | Covidence 대시보드 "Next up", GOV.UK start page | `ui.todo` 카드: 인디고 바탕·왼쪽 띠·알약 라벨로 다른 카드와 구분. 예시 프로젝트는 "미리 채워져 있음" |
| 선별·검토는 **대기열 표 + 상세** (목록에서 행을 고르면 아래/옆에 상세) | Rayyan·Covidence 스크리닝 큐, Elicit 표→상세 | 2단계 문헌 대기열·4단계 근거 대기열(`st.dataframe(on_select)`), 저장하면 다음 미검토로 이동 |
| 큰 숫자 타일 대신 작은 상태 칩 | Linear 필터 칩, Notion 속성 칩 | `ui.header` 칩 줄(추출 항목 4 · 읽을 쪽수 20 …). 큰 `st.metric` 타일은 검토 진행 등 진짜 KPI에만 |
| 단계의 단위와 질문을 머리에 명시 | Covidence "Title & abstract screening" vs "Full text review" vs "Extraction" | 2단계 "논문 한 편 단위 · 이 논문을 쓸까?" / 4단계 "값 한 건 단위 · 이 값이 원문과 맞나?" — 같은 2단 배치라 혼동되던 것을 글로 가른다 |
| 내부 코드는 사용자 낱말로 | Carbon status, KRDS 배지 | `exact_normalized`→"글자 그대로 일치" 등 `CODE_WORD`, 보고서·CSV도 같은 낱말 |

## 화면 구조

- **사이드바**: 제품 이름 → 프로젝트 선택·만들기 → 작업 단계(세로 목록, 상태 접두) → 프로젝트 경로. 단계 이름은 0.1.0과 같다(`1 · 조사 설계` … `6 · 비교·내보내기`).
- **머리 띠**: 단계 제목 한 줄 + 하는 일 한 문장 + 숫자 상자(이 단계의 현황). 숫자 상자는 테두리 있는 `st.metric`.
- **본문 2단**: 왼쪽 판단·입력, 오른쪽 원문. 비율 1 : 1.8.
- **문헌 선별의 근거 구절(0.2.1)**: 포함·제외 판단의 근거가 된 원문 문장을 한 줄에 하나씩 적으면 저장 때 `locate_anywhere`로 문서 전체에서 유일한 자리를 찾아 오른쪽 PDF에 근거 검토와 같은 주황 강조로 보인다. 못 찾은 구절은 경고로 남기고 판단은 그대로 저장한다 — 위치 확인은 기준 적합성 판단이 아니다. 「보여줄 근거 구절」을 고르면 쪽과 강조가 바뀐다.
- **카드**: `st.container(border=True)`. 그림자·그라데이션 없음.
- **표**: `st.dataframe` + `column_config`, 상태 열은 글자(뱃지 색은 셀에 쓰지 않음 — Streamlit 표는 뱃지 미지원).
- **문구**: 라벨은 명사구, 안내는 한 문장, 오류는 원인+해결. 개수 표현 대신 숫자 상자.

## 검증

- 자동: `pytest`(화면 시작 예외 검사 포함), `ruff`.
- 눈: 6단계를 브라우저에서 열어 머리 띠·뱃지·빈 상태·오류 인라인·PDF 강조를 확인하고 캡처를 `docs/screens/`에 남긴다.
- 덱(9주차)의 UI 캡처 7장은 이 판으로 다시 찍어야 한다.
